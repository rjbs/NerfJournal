# NerfJournal on JMAP for Tasks

This document describes how NerfJournal todos are encoded as JSCalendar
Task objects (RFC 8984) stored on a JMAP for Tasks server
(draft-ietf-jmap-tasks).  It is the contract between the app's local
model and the server, written ahead of the sync engine so the engine's
local schema can be designed against it.

It deliberately does not describe the sync engine itself: state strings,
push, the offline write queue, and conflict handling are a separate
piece of work.  Where a decision here constrains that work, it is called
out under "Left to the sync engine".

Status: draft, 2026-09-13; revised 2026-10-04 after probing a prototype
server.  Waiting on JMAP for Tasks support in Cyrus IMAP.

## Principles

1.  **The Task is the source of truth for a todo.**  The local SQLite
    database becomes a cache of Task objects plus client-only state.

2.  **Standard properties where they fit, vendor properties where they
    do not.**  Vendor properties use the prefix `nerfjournal.rjbs.cloud:`
    as RFC 8984 section 3.3 requires.

3.  **Only our own properties are ever written.**  Every write is a JMAP
    PatchObject touching named properties.  The client never replaces a
    whole Task, so properties it does not model survive a round trip
    through NerfJournal.

4.  **Reading is lenient, writing is strict.**  A Task created by another
    client, with none of our vendor properties, must still display
    sensibly.  A Task we write always carries the full encoding below.

5.  **Never write on read.**  Filling in a missing property on a foreign
    Task happens only when the user edits that Task, or the sweep
    cancels it.  Fetching is side-effect free.

## What lives where

| Concept        | Lives on the server as          | Notes                       |
|----------------|---------------------------------|-----------------------------|
| Todo           | a Task                          | this document               |
| Category       | a keyword on each Task          | color and order are local   |
| JournalPage    | nothing                         | client-only saved view      |
| TaskBundle     | nothing                         | client-only template        |
| BundleTodo     | nothing                         | becomes a Task when applied |
| Export group   | nothing                         | client-only                 |

Only one TaskList is used for now.  Categories are keywords rather than
TaskLists precisely so that splitting the journal across TaskLists
remains possible later without recoding categories.

## The Todo to Task mapping

The current local `Todo` has these fields:

    id, title, shouldMigrate, start, ending, categoryID, externalURL

with `ending` being nil (pending) or a `TodoEnding` of `day`, optional
`time`, and `kind` (done or abandoned).

### Identity

The Task's JMAP `id` is the todo's identity.  Local integer ids go away;
`Todo.id` becomes a String.  This changes the export JSON format and
every place the `nerf` CLI writes to SQLite directly.

The Task's `uid` is generated by the client on creation as a UUID.  It is
not otherwise used.

### taskListIds

A Task must belong to at least one TaskList; the server rejects a
create without one.  On create the client sets `taskListIds` to the
single configured list.  It never otherwise reads or writes the
property, so a Task another client has placed in several lists stays
there.

### title

`Todo.title` is the Task's `title`, verbatim.

### start

`Todo.start` is a civil date.  It is written as:

    "start": "2026-09-13T00:00:00",
    "showWithoutTime": true

with no `timeZone` property, so the start is floating.  On read, the
start day is the date part of `start`; any time component and any time
zone are ignored.

The `T00:00:00` suffix is required.  `start` is a LocalDateTime and a
bare date is rejected by the server.

A Task with no `start` is treated as starting on the civil day of its
`created` timestamp, converted in the client's current time zone.  This
is a read-side rule only; the client never writes a Task without
`start`.

`due` is neither written nor read.

### The future log

The future log is not a separate structure.  It is every pending Task
whose start day is after today.  This is unchanged from the current
model.

### Migration versus auto-cancel

`Todo.shouldMigrate` becomes the vendor property

    "nerfjournal.rjbs.cloud:autoCancel": true

with the opposite sense: `autoCancel` true means `shouldMigrate` false.
The property is a Boolean and defaults to false when absent, so a Task
created by any other client migrates, which is the behavior anyone not
using NerfJournal would expect from a task.

On read, the property is true only when its value is JSON `true`.  Any
other value, including a truthy string or number, is treated as absent.
The server does not validate vendor property types, so this rule is what
keeps a malformed value from cancelling a task.

The property is named for what the sweep does, which is set `progress`
to `cancelled`.  It is not named "autofail" because JSCalendar's
`failed` progress value is not used by NerfJournal (see below) and the
name should not suggest that it is.

Once a Task has ended, `autoCancel` has no effect.  The client still
writes it faithfully so that reopening a Task restores its original
behavior.

### The sweep

When today's journal page is created, the client cancels every Task that
is pending, has `autoCancel` true, and has a start day before today.
Each such Task receives

    "progress": "cancelled",
    "nerfjournal.rjbs.cloud:endedAt": "<its start day>"

The ending day is the Task's start day.  A non-migrating task is live on
exactly one day, so that is by definition the day it was abandoned.
(The current SQLite implementation uses the date of the last journal
page before today instead.  That agrees with the start day whenever the
todo was created on a page day, and is wrong otherwise; the move to the
start day is a small deliberate change.)

The sweep is idempotent and may run on any number of clients.  It makes
no reference to journal pages, which is what allows pages to stay
client-side.

### Ending kind: progress

The ending's kind is the Task's standard `progress` property.

| `progress`                            | `Todo.ending`                  |
|---------------------------------------|--------------------------------|
| absent, `needs-action`, `in-process`  | nil (pending)                  |
| `completed`                           | kind `done`                    |
| `cancelled`                           | kind `abandoned`               |
| `failed`                              | kind `abandoned` on read only  |

The client writes only `completed`, `cancelled`, and `needs-action`.  It
never writes `failed`.  A foreign Task marked `failed` displays as
abandoned; if the user then changes its ending, the client writes
`cancelled` or `completed` as appropriate.

Reopening an ended Task writes `progress` back to `needs-action` and
removes `endedAt` and `progressUpdated`.

### Ending time: endedAt

The ending's time is the vendor property

    "nerfjournal.rjbs.cloud:endedAt"

a String in one of two shapes:

*   A day-only ending, when the time of day is unknown (a resolution
    made on a past page, or the sweep):

        "2026-09-13"

*   A moment ending, when the completion was a real event with a known
    instant.  This is an RFC 3339 date-time with a numeric UTC offset,
    which carries exactly the `instant` and `offsetSeconds` of the local
    `Moment` type:

        "2026-09-13T14:03:22-04:00"

    An offset of `Z` is permitted and means `+00:00`.

In both shapes the ending's civil day is the first ten characters of the
string.  For a moment ending that day is the civil day at the recorded
offset, which is the same rule the local model uses.

A value that parses as neither shape is treated as absent, and the
fallback below applies.  The server stores whatever it is given.

A vendor property rather than the standard `progressUpdated` is used for
two reasons.  First, `progressUpdated` is a UTCDateTime and cannot
express a day-only ending.  Second, the JSCalendar revision in progress
deprecates it.

The client nonetheless sets `progressUpdated` to the instant of the
write whenever it changes `progress`, as a courtesy to other clients.
It is never read when `endedAt` is present.

The server does not maintain `progressUpdated` itself: changing
`progress` leaves the old value in place.  The client is therefore the
only thing keeping it honest, which is why the reopen rule above removes
it rather than leaving a stale completion instant behind.

`endedAt` is meaningful only when `progress` is `completed`,
`cancelled`, or `failed`.  If `progress` says the Task is pending, a
leftover `endedAt` is ignored on read.  This handles a foreign client
that reopens a Task without knowing to clear our property.

### endedAt fallback for foreign completions

When `progress` indicates an ended Task but `endedAt` is absent, the
ending day is derived, in order of preference, from:

1.  `progressUpdated`, if present;
2.  `updated`, which every JSCalendar object carries;
3.  the start day.

The chosen timestamp is converted to a civil day in the client's current
time zone, and the result is a day-only ending.  The start day is the
last resort, not the first, because a task that lived for a week and was
completed elsewhere should not appear on its first day's page as done.

Per principle 5, the derived value is not written back.

### Categories: keywords

`Todo.categoryID` becomes a keyword on the Task.  Keywords are a map of
String to Boolean; the key is

    "nerfjournal:category:<category name>"

where the name is the local Category's `name`, exactly, and matching is
case-sensitive.  A categorized Task carries exactly one such keyword.
An uncategorized Task carries none.

    "keywords": {
        "nerfjournal:category:Work": true
    }

Category color and sort order remain local and are not synced.

Rules:

*   **On write**, the client sets its one category keyword and removes
    any other keyword with the `nerfjournal:category:` prefix.  Keywords
    without that prefix are left alone.

*   **Multiple category keywords on read**: the Task is assigned to the
    matching Category with the lowest `sortOrder`.  The others are
    ignored until the next write cleans them up.

*   **Unknown category on read**: a keyword `nerfjournal:category:X`
    where no local Category is named `X` causes the client to create a
    Category named `X` with a default color, appended to the sort order.
    This makes categories sync by name between two NerfJournal clients
    without any category object on the server.  It is the one exception
    to principle 5, and it writes only to local state.

*   **Renaming a Category** rewrites the keyword on every Task carrying
    it, in a single JMAP set.

*   **Deleting a Category** removes its keyword from every Task carrying
    it.

### External URL: links

`Todo.externalURL` becomes an entry in the Task's `links` map under the
fixed key `nerfjournal-external`:

    "links": {
        "nerfjournal-external": {
            "@type": "Link",
            "href": "https://example.com/ticket/123",
            "rel": "related"
        }
    }

On read, the journal's link is the `href` under that key.  If the key is
absent and the Task has exactly one link, that link is shown instead.
Other links are preserved and not displayed.

Clearing the URL removes the `nerfjournal-external` entry only.

### Properties never written

`description`, `due`, `priority`, `alerts`, `recurrenceRules`,
`participants`, `locations`, `percentComplete`, `estimatedDuration`, and
anything else not named in this document are neither read nor written.
Per principle 3 they survive untouched.

## Summary of properties

Standard:

| Property          | Written | Read | Purpose                          |
|-------------------|---------|------|----------------------------------|
| `@type`           | yes     | yes  | always `"Task"`                  |
| `taskListIds`     | create  | no   | the configured list              |
| `uid`             | create  | no   | UUID                             |
| `title`           | yes     | yes  | todo title                       |
| `start`           | yes     | yes  | civil start day                  |
| `showWithoutTime` | yes     | no   | always true                      |
| `progress`        | yes     | yes  | pending / done / abandoned       |
| `progressUpdated` | yes     | fallback | courtesy write, fallback read |
| `keywords`        | yes     | yes  | category                         |
| `links`           | yes     | yes  | external URL                     |
| `created`         | no      | fallback | start day for foreign Tasks  |
| `updated`         | no      | fallback | ending day for foreign Tasks |

Vendor, all prefixed `nerfjournal.rjbs.cloud:`:

| Property     | Type    | Default | Purpose                              |
|--------------|---------|---------|--------------------------------------|
| `autoCancel` | Boolean | false   | cancelled by the sweep if not done   |
| `endedAt`    | String  | derived | day-only or moment ending time       |

## Worked examples

A migrating todo, pending, in the Work category, with a URL:

    {
      "@type": "Task",
      "uid": "9d2f5b1e-3e4a-4c5b-8f7e-1a2b3c4d5e6f",
      "title": "Review the release notes",
      "start": "2026-09-13T00:00:00",
      "showWithoutTime": true,
      "keywords": { "nerfjournal:category:Work": true },
      "links": {
        "nerfjournal-external": {
          "@type": "Link",
          "href": "https://example.com/pr/42",
          "rel": "related"
        }
      }
    }

The same todo, completed at a known moment:

    {
      ...,
      "progress": "completed",
      "progressUpdated": "2026-09-13T18:03:22Z",
      "nerfjournal.rjbs.cloud:endedAt": "2026-09-13T14:03:22-04:00"
    }

A habitual, non-migrating todo that was not done, after the sweep:

    {
      "@type": "Task",
      "uid": "...",
      "title": "Read the on-call log",
      "start": "2026-09-12T00:00:00",
      "showWithoutTime": true,
      "nerfjournal.rjbs.cloud:autoCancel": true,
      "progress": "cancelled",
      "progressUpdated": "2026-09-13T12:00:07Z",
      "nerfjournal.rjbs.cloud:endedAt": "2026-09-12"
    }

A born-done todo (something done that was never planned) is created in
one write with `progress`, `progressUpdated`, and a moment `endedAt`
equal to its creation.

## The journal page in Task terms

A page for civil day D shows every Task with start day on or before D
that is either pending or has an ending day on or after D.  The future
log for D is every pending Task with start day after D.  Both are
evaluated against the local cache; neither needs a server-side query.

## One-time migration from SQLite

Each existing `todo` row becomes one Task:

| SQLite column   | Task property                                  |
|-----------------|------------------------------------------------|
| `id`            | dropped; the new JMAP id is recorded locally   |
| `title`         | `title`                                        |
| `shouldMigrate` | `nerfjournal.rjbs.cloud:autoCancel` = NOT it   |
| `start`         | `start` + `showWithoutTime`                    |
| `ending.kind`   | `progress`: done to `completed`, abandoned to `cancelled` |
| `ending.day`, `ending.time` | `endedAt`: moment form when `time` is present, else day form |
| `categoryID`    | `keywords` entry from the Category's name      |
| `externalURL`   | `links["nerfjournal-external"]`                |

`progressUpdated` is set to the ending instant for moment endings and
omitted for day-only endings, since no true instant exists.

## Left to the sync engine

*   Whether the client or the server sets `created` and `updated`, and
    what the client does with `updated` on patch.
*   How the `nerf` CLI writes: to the local cache for the engine to push,
    or to the server directly.
*   Whether the local cache stores Tasks in JSTask shape or in `Todo`
    shape with a codec at the boundary.  This document assumes a codec
    exists somewhere and defines what it must do.
*   Undo, which becomes a compensating patch rather than a local
    transaction rollback.
*   Conflict resolution when two clients edit one Task.  The properties
    here are small and independent, so property-level last-writer-wins
    is probably enough.

Observed on the prototype server, 2026-10-04, and relevant to the engine:

*   Task/query reports `canCalculateChanges` false, so the engine must
    use Task/changes against the local cache rather than
    Task/queryChanges.
*   There is no `keyword` filter condition, so categories are filtered
    locally.  `progress` filters take an array of strings; `before` and
    `after` take a LocalDateTime, not a UTCDateTime.
*   Unknown properties, prefixed or not, are stored and returned without
    validation.  Nothing on the server enforces this document.
*   Removing the last entry from `links` leaves an empty `links` map.
*   EventSource push works and sends a StateChange on connect.
